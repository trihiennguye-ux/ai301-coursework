# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff stays inside the plan | Every changed file and hunk in the diff, and the commit list, read against the plan's scope, "Not in scope", and "Files" lines and any deviation note (Plan fidelity family in `references/evidence-guide.md`) | Every changed file and every behavior-changing hunk is one of: a change the plan's scope or Files line names; the test for that change; an artifact the repo asks for with this kind of change (changelog or release-note entry, i18n string, regenerated docs); or a departure covered by a deviation note, in the plan or in the description, that says what differs from the plan and why the fix needed it. Fail if the diff adds anything else: a new option, flag, or setting; a refactor or rename of code the fix does not need; a change in a file the plan does not name; anything the plan lists as not in scope; or a different approach from the one the plan committed to. A description that merely mentions the extra work ("cleaned up some formatting while I was in there") is not a deviation note. Whitespace-only and debris hunks inside planned files are graded by "Diff is reviewable", not here | required |
| Plan delivered or shortfall disclosed | The plan's scope and Files lines (each numbered change, test, and doc it promises) read against the diff's changed files, the description, and any deviation note (Plan fidelity family) | Every deliverable the plan names is present in the diff, or the plan or the description says plainly that it is not in this PR and why. A PR that does less than the plan and says so passes: a disclosed, bounded shortfall is honest work, and so is a limit the plan itself already deferred. Fail if a planned deliverable (a second code change, the docs page, the test) is missing from the diff and nothing in the plan or description says so | required |
| Description matches the diff | Each concrete claim the title and description make about what the diff contains, read against the diff as shown (Plan fidelity family). The diff in the package is the whole diff | Every checkable claim about the diff's contents is true of the diff: files or entries said to be added are there ("CHANGELOG entry included", "tests added", "docs updated"), and fidelity claims hold ("implements the plan exactly", "in full", "no other changes", "no changes beyond it"). Fail if the description says something is in the diff that is not, or claims exact or complete fidelity while the diff does more or less than the plan. Claims about test results belong to "Evidence shows the fix", not here | required |
| Evidence shows the fix | The test-evidence section read against the plan's test plan and the repro evidence the plan built on (Test evidence family) | Two things, both needed. (1) The evidence shows the reproduced behavior re-run after the change: it names the command or action from the repro and the specific result observed, and that result is the expected-after the plan's test plan states. A transcript, or prose that names the action and the exact outcome, both count. (2) Every other item the test plan names is reported with its outcome: each additional failure mode shown the same way, each control stated, and the repo's own suite or checks reported as run. Fail if there is no evidence; if the evidence is a feeling with no action and no result ("tested locally, works now", "verified on my machine", "all tests pass" alone); if it shows a different case from the one reproduced (only the control, a different request, general use over time); if a failure mode the test plan names is never shown; if the suite the plan or repo asks for is never reported; or if the author says the repro was not run on the fix | required |
| Diff is reviewable | The unified diff hunk by hunk and the commit list (Diff quality family) | Every hunk serves the change: the fix, its tests, or an artifact the repo asks for. Fail if the diff carries debris or unrelated hunks: debug prints or logging left in non-test code, commented-out code, added TODO or WIP markers, hunks that only re-indent, re-wrap, or reformat lines the fix does not change, a rewrite of unrelated code, or a "cleanup"/"misc" commit touching code outside the fix. Not debris: a comment explaining the fix, output statements that are a test's own fixture, and lines the fix itself had to change | required |
| Repo asks honored | The repo-facts "pull requests" line (live: the repo's PR template, `docs/CONTRIBUTING.md`, and the house rules in `scope.md`) read against the description, the title, and the diff's changed files (Standards and comms family) | Every stated ask that can be checked from the package is met: each section or checklist item the template asks for is identifiable in the description with real content, or marked n/a with a reason; the issue is referenced in the form asked ("closes #N", "fixes #N"); a changelog, whatsnew, or release-note entry the repo asks for with this kind of change is in the diff; tests are in the diff when the repo asks for tests; the title follows a stated title convention. Passes when the repo has no template and states no asks. Fail if a template section or required checklist item is absent or left as boilerplate, or an asked-for artifact is missing from the diff. Not graded here: process asks the package cannot show (a signed CLA, a vouch flow, prior discussion approval), and "if appropriate" asks that do not apply to this change (screenshots for a non-UI fix) | required |
| AI-policy compliance | The repo-facts "contribution policy" line (live: `docs/CONTRIBUTING.md` and the PR template's disclosure section) read against the description text (Standards and comms family); every package is treated as AI-assisted work | An outright ban on AI-assisted contributions fails. A policy that requires AI use to be disclosed passes only if the description discloses it with what the policy asks for (the tool, the extent, wherever it says). A policy that only asks for understanding, responsibility, or human-written words, or a repo with no stated AI policy, passes with or without a disclosure. A template disclosure section passes only when it is filled in | required |
| Maintainer direction respected | Thread highlights authored by OWNER, MEMBER, COLLABORATOR, or CONTRIBUTOR, and any policy a maintainer restated in the thread, read against the diff and the description (Standards and comms family) | Passes unless the PR does something a maintainer in the thread rejected or ruled out (for example, uses an API a maintainer said cannot ship), or goes a different way from a direction a maintainer chose without the description saying why. Passes when the thread has no maintainer direction. Comments from non-maintainers (NONE) and bots are not direction | required |
| Title and commits name the change | The PR title and the commit list (Diff quality family) | The title says what behavior changed, and each commit message names what that commit does. Fails on a title or commits that say nothing about the change ("wip", "fix", "fixed the bug!!") | preferred |

Grade each check on what the package shows. Grade `unclear` only when
the part of the package the check reads is missing, so the condition
cannot be decided either way; when the part is there and the condition
is not shown to be met, the grade is `fail`.

## Verdict rule

Accept only if every `required` check passes. Any `required` check
that fails, or comes back `unclear`, rejects the package: `unclear` is
treated the same as fail, since a PR I cannot verify from the package
is not a PR that is ready to submit. The `preferred` check never
changes the verdict; its grade is reported so the author can tighten
the title and commits before opening the PR.

Doing less than the plan is not by itself a reason to reject: a PR
that discloses its shortfall and passes every required check is
accepted.
